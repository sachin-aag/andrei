Chat harness architecture

The harness is the server-side control plane around report chat. It is not the Gemini model, and it is not the PDF search index. It decides intent, retrieval shape, which tools exist on each step, and whether a drafted fact is allowed to persist.

Mental model. The LLM proposes. The harness constrains. The engineer Applies. There is no commit edit path: live report chat always writes ai_fix comments plus red/green marks. Nothing lands in report_sections until Apply / Dismiss.

1. Three layers that people mix up

Figure 1. Chat stays the control plane. Do not replace agentic grep with a standalone search product. How files become rows: briefing 3. How search reads those rows: briefing 4.

What the harness owns

  • Latest-turn intent: social | read | write
  • Retrieval policy: focused | adaptive | comprehensive
  • Per-step activeTools / optional toolChoice
  • Citation ledger + groundDraftText
  • In-turn message compaction and tool-result budgets
  • 270s wall-clock abort (not a tool-step cap)

What it does not own

  • TipTap section JSON (autosave PATCH)
  • Criteria eval / suggestion generation
  • PDF bytes / Vertex ingest / embeddings
  • Analytics worksheet (separate /analytics/chat, same ChatPanel)
  • Apply/Dismiss merge (src/lib/suggestions)

2. Request lifecycle

Entry point: src/app/api/reports/[reportId]/chat/route.ts. One HTTP POST is one turn. A turn may contain many steps (model → tools → model).

Figure 2. One POST = one turn. Cost is dominated by resending system + tool schemas + accumulated tool results on every step.
