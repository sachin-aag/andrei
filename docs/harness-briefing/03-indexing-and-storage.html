Indexing and storage

This briefing is the write path: how a PDF or Word file becomes rows and indexes in Postgres. Briefing 4 is the read path: how search_documents queries those same rows. There is no separate search cluster. Chat stays the control plane.

QuestionWhat we actually have
Hosted vector DB (Pinecone, Weaviate, Elastic kNN)?No. A vector(768) column on document_chunks in the same Postgres (Neon or Docker). Index: HNSW, cosine ops. Query uses embedding <=> query::vector.
BM25?No. English Postgres full-text search: GIN on to_tsvector('english', contextual_text), query via websearch_to_tsquery, rank via ts_rank_cd. BM25 as a third arm is deferred (docs/retrieval.md).
Elasticsearch / standalone search product?No. Do not replace agentic grep with one. Hybrid retrieval already runs under chat.
Is the report body indexed?No. TipTap JSON lives in report_sections. Chat uses read_section. Only attachment pages are chunked.
Two stores, one pipeline. Object storage holds bytes (preview, download, re-ingest). Postgres holds searchable text + vectors. Search never greps GCS. If ingest did not finish, there is nothing to retrieve.

1. Overall: write path then read path

Figure 1. Indexing is ingest writing Postgres. Retrieval is SQL against those rows. Do not invent a third system in between.

Join is always the report’s live ingest: report_attachments.active_ingest_run_id = document_chunks.ingest_run_id. Superseded runs are invisible to search. Library links join by asset_id when set; eval / legacy rows with null asset_id join on attachment_id. Citations stay filename + page — chunk ids change on re-ingest. Living plans: docs/document-ingest-pipeline.md (write) · docs/retrieval.md (read). Code: run-document-ingest.ts · retrieval.ts.

2. How input documents are processed

Entry: startDocumentIngest → runDocumentIngest (src/lib/attachments/run-document-ingest.ts). Extract + embed are Vertex-only (GOOGLE_VERTEX_PROJECT). A Gateway key is not enough. Stub: ALLOW_TEST_STUB_DOCUMENT_INGEST.

Figure 2. Extract model is Gemini Flash-Lite at Vertex global. OCR is a regional Document AI processor. Embeddings stay on GOOGLE_VERTEX_LOCATION (often us-central1). Do not conflate those locations.

3. What Postgres stores after ingest

Searchable evidence is three grains. Metadata is filterable columns (file / page / span), not extra prose stuffed into every chunk. Chunks inherit page columns via pageId.

Figure 3. list_attachments is not this index. It walks the Attachments tree (count / folders / types / status / filename). Which files mention a fact inside a PDF is still chunk search.

How a page becomes chunks

chunkDocumentPages in chunk-pages.ts. Transcript and visual interpretation are chunked as separate sources so a figure caption does not drown the quote, and ranking can prefer quote over visual_interpretation.

There is no BM25 index to look at. Keyword search is Postgres tsvector / tsquery with English stemming. That is closer to a Lucene TF-IDF variant than Okapi BM25. Adding BM25 would be a new arm fused with vector + FTS — explicitly deferred, not missing by accident.

4. Status until search can see the file

Attachment: uploading → validating → queued → processing → ready (or failed). Ingest run: pending → running → ready | failed | cancelled. A new successful run marks the previous ready run superseded. Chat lists ready docs in the context map (filename + sanitized documentSummary). Untrusted extract text is sanitized in chat/tools, not in the attachments package.
